在现实中，很多查找操作并不是在内存中完成的，而是要访问磁盘或数据库。相比内存，磁盘的读写代价非常高，必须尽可能减少查找过程中磁盘的访问次数。此时，二叉排序树就显得有些“力不从心”了，因为其高度容易过大，导致频繁的磁盘访问

为了解决这个问题，人们提出了一种多路平衡查找树 —— B树（Balanced Tree 或 Bayer Tree）



# B树（B-树）
简单理解，B树是“多路版本”的平衡查找树，或者叫“平衡多叉树”。如果将二叉排序树看成是“每个节点最多两个分支”的树，那么B树允许每个节点有多个关键字和多个孩子，这种结构能有效压缩树的高度。  

![](/images/yuque/67e6619570a27c92f57602fb3eb42c00.png)

上图是一个三阶B树

## 性质
 一个m阶的B树满足以下性质：

1. 每个节点最多有 m 个孩子

2. 每个非根非叶子节点至少有 ⌈m/2⌉ 个孩子

3. 每个非叶子节点有 k 个孩子，就有 k-1 个关键字

4. 关键字按照中序遍历是有序的



对于性质三反过来说，每个非叶子节点有k个关键字，那么就有k+1个孩子

对于性质一来说，有m个孩子，最多就有m-1个关键字

对于B树，所有叶子节点在同一层

## 区间
另外还有一点需要注意的是：关键字在节点中是排好序的，孩子在关键字之间穿插，每个孩子对应一个“区间”。

T0：所有值 < 17

T1：所有值 ∈ (17, 35)

T2：所有值 > 35

# B树的操作-插入
（1）查找插入位置（从根开始）

找到要插入的关键字应该落在哪个叶子节点

（2）将关键字插入该叶子节点的合适位置

如果该节点未满，直接插入，结束

如果插入后超出最大关键字数（即满了）→ 触发分裂

（3）分裂：关键字“上移”，节点一分为二

中间的关键字上升到父节点

分裂产生两个子节点，平分原数据

父节点接收中间关键字及新子节点指针

（4）父节点若满，继续向上传递（递归分裂）

最终可能导致根节点分裂 → 树高增加

# B树的操作-删除
（1）查找目标关键字的位置（从根开始）

从根节点开始查找目标关键字

若找到关键字：如果该节点是叶子节点，可直接删除

如果该节点是非叶子节点 ，需转化为在叶子节点中的删除

若未找到关键字 ，递归进入对应子节点继续查找

![](/images/yuque/c14ee5192c54b6c4b593f48f43b1c8db.png)

![](/images/yuque/8c5616996f1f5c64abd92b66feb3e486.png)



（2）若关键字位于非叶子节点 → 转为删除其前驱或后继关键字

从该节点的左子树中找出最大值（前驱）

或从右子树中找出最小值（后继）

用该值替换关键字，然后在叶子节点中递归删除前驱/后继值

目的：让真正的删除操作都发生在 叶子节点，便于处理

![](/images/yuque/2e31c262da569f7a6427f4322d210b86.png)

![](/images/yuque/6d7dfd7ab64adddff24d678a5053d9ec.png)



（3）删除前，判断目标子节点是否安全（关键字个数 ≥ ⌈m/2⌉）

如果不足，可能会导致删除后违反最小关键字约束 → 需要提前“填充”或“合并”，具体见第（4）步



（4）不足时如何“填充”目标子节点

假设要进入第 i 个子节点 C[i] 删除：

情况一：左兄弟 C[i-1] 存在，且关键字数 > ⌈m/2⌉−1 → 借用

从父节点拿一个关键字下调至 C[i]；

左兄弟把自己的最大关键字上调到父节点；  
若有子树，调整指针结构

情况二：右兄弟 C[i+1] 存在，且关键字数 > ⌈m/2⌉−1 → 借用  
从父节点拿一个关键字下调至 C[i]

右兄弟把自己的最小关键字上调到父节点

若有子树，调整指针结构

情况三：两边兄弟都不足 → 合并

将当前子节点与一个兄弟节点合并成一个新节点

父节点中对应的关键字也下调进入合并节点

父节点关键字数量减少 → 若也不足，再继续向上传递

# B树的操作-查找
在学习 B 树时，查找操作反而不是最难的，相比之下，插入和删除的逻辑才是真正体现 B 树结构特性的地方

B 树的查找过程，其实并不复杂。本质上，它是一种多路查找：每一个结点中不仅有多个关键字，还有多个指向子树的指针。因此，每次在结点中查找时，都不是简单地“往左”或“往右”，而是根据关键字的数量进行“区间判断”， 从而决定该走哪一棵子树



（1）从根节点开始，逐层向下查找

在当前结点中，从左到右依次比较关键字：

如果等于某个关键字，查找成功

如果小于某个关键字，就转入该关键字左边的子树

如果大于所有关键字，就转入最右边的子树

（2）继续在子树中重复上述过程，直到查找成功或遇到叶子节点

若在叶子节点中也没有找到，说明目标关键字不存在于该 B 树中

若在中途命中关键字，查找结束，返回该位置

（3）整个过程本质上是“在结点内查找 + 递归进入子树”交替进行，直到命中或结束

可以将 B 树的查找过程类比为“查电话本”



# 使用B树的好处
减少磁盘读写次数：由于节点内存储多个关键字，树的高度被显著降低，从而减少了磁盘访问

适用于大数据量场景：B 树特别适用于数据库索引和文件系统等需要高效读写大量数据的应用



# B+树
B+树其实是 B 树的一个变种，是在数据库系统、文件系统中应用最广泛的一种平衡查找树结构。它的本质仍然是“分层、多分支、平衡”的，但与 B 树相比，它在结构上做了两处关键性的优化：

（1）所有关键字只出现在叶子结点中，非叶子结点仅用于索引

（2）所有叶子结点按大小顺序通过指针连接，形成有序链表

# B+树的优势
更适合磁盘读取：由于非叶子节点不存储实际数据，单个磁盘块可以容纳更多关键字， 从而减少 IO 次数

范围查找更高效：只需在叶子结点链表中顺序扫描即可，无需回溯中间节点

查询结果更稳定：所有数据都集中在叶子节点，查找路径一致，避免“某些数据层数较深”的情况
